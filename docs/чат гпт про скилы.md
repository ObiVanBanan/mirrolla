Серёга, для гибкого ассистента нужен не один огромный промпт под все вопросы, а такая схема:

```text
Planner → выбирает skill
Executor/Code Interpreter → считает факты
Validator → проверяет полноту результата
Reporter LLM → формирует понятный ответ менеджеру
```

У тебя уже загружается отдельный `SKILL.md` в зависимости от выбранного skill — это хорошая основа. 

Проблема сейчас в том, что после `SKILL.md` идёт жёсткий общий сценарий: объединить Ozon, посчитать заказы по дням и построить один конкретный график. Он применяется даже к остаткам, отзывам и другим вопросам. 

## 1. Универсальный контракт результата

Вместо того чтобы для каждой гипотезы возвращать только `detail` и несколько чисел, используй универсальный массив `findings`.

Он подходит и для товаров, и для отзывов:

```json
{
  "answer_status": "answered",
  "answer": "Прямой ответ на вопрос менеджера",
  "findings": [
    {
      "entity_type": "product",
      "entity_id": "ЦБ-00007397",
      "name": "Название товара",
      "priority": "high",
      "reasons": [
        "Продажи снизились на 37%",
        "Доля отмен выросла с 4% до 12%"
      ],
      "metrics": {
        "sales_current": 120,
        "sales_previous": 190,
        "sales_change_pct": -36.84
      },
      "recommended_action": "Проверить остатки, цену и причины отмен",
      "evidence": [
        {
          "dataset": "ozon_sales",
          "period": "последние 30 дней",
          "description": "120 полученных заказов против 190 в предыдущем периоде"
        }
      ]
    }
  ],
  "aggregates": {
    "total_checked": 3855,
    "problem_count": 14
  },
  "hypothesis_results": [],
  "limitations": []
}
```

Основная идея:

* `answer` — прямой ответ;
* `findings` — конкретные товары или отзывы;
* `metrics` — рассчитанные показатели;
* `reasons` — почему объект попал в результат;
* `recommended_action` — что делать менеджеру;
* `aggregates` — общая статистика.

## 2. Универсальный блок для Executor

Замени текущие фиксированные требования и пошаговый план на этот блок:

```python
UNIVERSAL_ANALYSIS_INSTRUCTIONS = """
## Цель анализа

Ответь непосредственно на вопрос менеджера на основе загруженных данных.

Результат должен содержать не только общие числа, но и конкретные сущности:
товары, отзывы, категории или другие объекты, которые отвечают условиям вопроса.

## Основные правила

1. Сначала изучи структуру всех загруженных файлов:
   - имена файлов;
   - названия колонок;
   - типы данных;
   - диапазоны дат;
   - количество строк;
   - возможные ключи объединения.

2. Определи единицу анализа в зависимости от вопроса:
   - товар;
   - товар и день;
   - товар и период;
   - отзыв;
   - категория;
   - складской остаток.

3. Все показатели по товарам рассчитывай отдельно для каждого товара.

4. Нельзя применять показатель всего портфеля к отдельному товару,
   кроме случаев, когда портфель используется как явно обозначенный benchmark.

5. При объединении файлов:
   - нормализуй ключи через astype(str).str.strip();
   - проверь количество совпавших и несовпавших записей;
   - не объединяй по названию, если существует код или артикул;
   - не придумывай значения для несовпавших объектов.

6. Проверь все гипотезы из плана, но итоговый результат должен отвечать
   на исходный вопрос менеджера, а не просто перечислять статусы гипотез.

7. Если вопрос предполагает список объектов, обязательно верни findings.
   Одного count недостаточно.

8. Для каждого finding верни:
   - entity_type;
   - entity_id;
   - name;
   - priority;
   - reasons;
   - metrics;
   - recommended_action;
   - evidence.

9. Верни до 20 наиболее важных findings.
   Если найдено меньше 20 объектов — верни все.

10. Отсортируй findings по бизнес-приоритету:
    - сначала критические;
    - затем высокие;
    - затем средние;
    - затем низкие.

11. В reasons используй конкретные значения.

Плохо:
"У товара снизились продажи."

Хорошо:
"Полученные заказы снизились со 190 до 120, падение составило 36.8%."

12. В recommended_action укажи конкретное действие менеджера.

13. Если необходимых данных нет:
    - не делай предположений;
    - установи answer_status="not_enough_data" или "partial";
    - перечисли отсутствующие данные в limitations;
    - объясни, какие данные необходимы для ответа.

14. График создавай только тогда, когда он помогает ответить на вопрос.
    График не является обязательным для каждого skill.

## Формат результата

В конце выведи только валидный JSON:

{
    "answer_status": "answered | partial | not_enough_data",
    "answer": "Прямой ответ на вопрос менеджера",
    "findings": [
        {
            "entity_type": "product | review | category",
            "entity_id": "идентификатор",
            "name": "название",
            "priority": "critical | high | medium | low",
            "reasons": ["причина с конкретными цифрами"],
            "metrics": {},
            "recommended_action": "конкретное действие",
            "evidence": [
                {
                    "dataset": "название источника",
                    "period": "анализируемый период",
                    "description": "фактическое подтверждение"
                }
            ]
        }
    ],
    "aggregates": {},
    "hypothesis_results": [
        {
            "hypothesis_id": "H1",
            "title": "Название",
            "confirmed": true,
            "detail": "Вывод",
            "data": {}
        }
    ],
    "limitations": []
}

## Проверка перед ответом

Перед выводом JSON проверь:

1. answer действительно отвечает на исходный вопрос.
2. Если вопрос просит товары или отзывы — findings не пустой.
3. Каждый finding содержит идентификатор и конкретные причины.
4. В reasons используются реальные рассчитанные показатели.
5. Все рекомендации основаны на данных.
6. Портфельные показатели не выданы за показатели отдельного товара.
7. Отсутствующие данные явно указаны.
"""
```

## 3. Содержимое каждого `SKILL.md`

Общий промпт определяет формат, а `SKILL.md` должен определять конкретные расчёты.

Используй для каждого skill одну структуру:

```markdown
# Название skill

## Какие вопросы обслуживает

## Бизнес-решение

## Единица анализа

## Обязательные датасеты

## Дополнительные датасеты

## Метрики

## Правила классификации

## Поля findings

## Рекомендации

## Когда данных недостаточно

## Подходящий график
```

### `sales-diagnostics/SKILL.md`

Для вопроса:

> Почему снизились продажи товара?

```markdown
## Единица анализа

Товар и сравниваемый период.

## Метрики

Для каждого товара рассчитать:

- полученные заказы текущего периода;
- полученные заказы предыдущего периода;
- изменение количества и изменение в процентах;
- отмены текущего и предыдущего периода;
- долю отмен;
- количество дней без продаж;
- среднюю оценку;
- количество негативных отзывов;
- текущий остаток, если доступен.

## Возможные причины

Причина подтверждается только цифрами:

- снижение количества заказов;
- рост доли отмен;
- отсутствие остатка;
- увеличение дней без продаж;
- ухудшение рейтинга;
- рост негативных отзывов;
- сезонность или разовый всплеск предыдущего периода.

## findings

Вернуть товар, показатели текущего и предыдущего периодов,
подтверждённые причины падения и рекомендуемое действие.
```

## 4. Некоторые вопросы пока нельзя корректно обработать

В текущем описании Ozon-файлов есть артикул, заказ, статус, отзыв, дата и оценка. В нём нет истории цен, себестоимости, скидок или цен конкурентов. 

Поэтому вопрос об изменении цены на текущих данных корректно не решить.

Аналогично для вопроса «растут быстрее рынка» нужен внешний market benchmark. Без него можно ответить только:

```text
Товар растёт быстрее среднего по портфелю Mirrolla
```

Но нельзя утверждать:

```text
Товар растёт быстрее рынка
```

## 6. Добавь семантическую валидацию

Одного промпта недостаточно. Модель может снова вернуть только количество.

После парсинга JSON проверяй результат:

```python
LIST_RESULT_SKILLS = {
    "inventory-planning",
    "production-planning",
    "growth-analysis",
    "review-monitoring",
    "pricing-analysis",
}


def validate_analysis_result(
    parsed: dict,
    skill: str,
) -> list[str]:
    errors = []

    if not parsed.get("answer"):
        errors.append("Отсутствует прямой ответ в поле answer")

    if skill in LIST_RESULT_SKILLS and not parsed.get("findings"):
        errors.append(
            "Вопрос требует список конкретных объектов, "
            "но findings пустой"
        )

    for index, finding in enumerate(parsed.get("findings", [])):
        if not finding.get("entity_id"):
            errors.append(
                f"findings[{index}]: отсутствует entity_id"
            )

        if not finding.get("reasons"):
            errors.append(
                f"findings[{index}]: отсутствуют причины"
            )

        if not finding.get("metrics"):
            errors.append(
                f"findings[{index}]: отсутствуют метрики"
            )

    return errors
```

Если ошибки есть, отправляй continuation через `previous_response_id`:

```python
correction_prompt = f"""
Результат не прошёл проверку:

{json.dumps(validation_errors, ensure_ascii=False)}

Исправь результат.

Не повторяй весь анализ, используй уже рассчитанные данные.
Верни полный валидный JSON.
"""
```

## 7. Раздели расчёт и красивый ответ

Code Interpreter должен возвращать структурированные факты, а отдельная LLM — отвечать менеджеру.

Промпт Reporter:

```python
REPORTER_PROMPT = """
Ты бизнес-аналитик маркетплейсов Mirrolla.

Ответь на исходный вопрос менеджера, используя только предоставленный
JSON анализа.

Правила:

1. Сначала дай прямой ответ в 1-3 предложениях.
2. Затем перечисли наиболее важные findings.
3. Для каждого объекта назови:
   - артикул или ID;
   - название;
   - конкретную причину;
   - основные показатели;
   - рекомендуемое действие.
4. Не придумывай отсутствующие данные.
5. Не пересказывай технические подробности Python.
6. Если answer_status не answered, явно объясни,
   каких данных не хватает.
"""
```

В итоге ассистент будет отвечать примерно так:

```text
Заканчиваются 14 товаров. У 5 товаров запас менее чем на 3 дня,
ещё 9 закончатся в течение недели.

1. ЦБ-00007397 — остаток 4 шт.
   Продажи: 17 шт. за 7 дней.
   Запаса хватит примерно на 1,8 дня.
   Рекомендация: заказать 42 шт. на горизонт 21 день.

2. ЦБ-00005124 — остаток 0 шт.
   За последние 7 дней было 11 продаж.
   Рекомендация: срочно пополнить запас.
```

Главный принцип: **универсальным должен быть формат результата, а не метод анализа**. Методика расчёта остаётся внутри соответствующего `SKILL.md`.
