Серёга, фиксируем концепцию, но **режем её до демонстрационного MVP**, который реально собрать за три дня.

# Концепция MVP

**Mirrolla AI Data Analyst** — агент, который:

1. получает вопрос менеджера;
2. изучает доступные данные;
3. выбирает аналитический skill;
4. формирует гипотезы и план анализа;
5. показывает план человеку;
6. после подтверждения запускает Python-анализ в изолированной среде;
7. возвращает выводы, таблицы, графики и рекомендации.

```text
Вопрос менеджера
        ↓
Planning Agent
        ↓
Гипотезы + план
        ↓
Human-in-the-Loop
        ↓
Execution Agent
        ↓
Python sandbox
        ↓
Результаты и рекомендации
```

Для выполнения анализа берём OpenAI Code Interpreter: он умеет запускать Python в изолированном контейнере, работать с загруженными файлами, строить графики и повторно исправлять неудачно написанный код. Это избавляет нас от разработки собственного небезопасного исполнителя Python. ([OpenAI Developers][1])

Human-in-the-Loop реализуем через LangGraph: `interrupt()` позволяет остановить workflow, сохранить состояние и продолжить после решения пользователя. Для локального MVP можно использовать SQLite-checkpointer. ([Docs by LangChain][2])

# Что входит в MVP

## 1. Интеграция с тестовой 1С

Read-only клиент:

```text
get_products()
get_balances()
get_sales(date_from, date_to, codes)
```

Он получает:

* каталог;
* остатки;
* продажи.

Полученные данные сохраняются в нормализованном виде.

Важно: из описания пока непонятно:

* используется `GET` или `POST`;
* куда передаётся `ИмяФункции`;
* какой точный JSON тела;
* какой формат даты;
* как выглядит ошибка;
* используется ли HTTP Basic Auth;
* возвращается обычный JSON или структура 1С.

Поэтому первый технический шаг — подключиться к VPN и выполнить разведку API через `curl` или Postman.

## 2. Загрузка предоставленных выгрузок

Поддерживаем:

```text
WB sales
Ozon sales
stocks
products
reviews
```

На входе допускаем CSV или Excel. После импорта переводим в единый формат Parquet:

```text
data/prepared/
├── products.parquet
├── sales.parquet
├── stocks.parquet
├── reviews.parquet
└── business_rules.json
```

WB и Ozon сопоставляем с 1С:

```text
WB article   → articleWb
Ozon article → articleOzon
GTIN         → gtin
Основной ID  → code из 1С
```

## 3. Planning Agent

Агент не начинает вычисления сразу. Сначала возвращает структурированный план:

```json
{
  "question": "Почему снизились продажи шампуня с кератином?",
  "product_codes": ["00-000123"],
  "period": {
    "current_days": 14,
    "comparison": "previous_equal_period"
  },
  "skill": "sales-decline-analysis",
  "hypotheses": [
    {
      "id": "H1",
      "title": "Дефицит остатков",
      "datasets": ["sales", "stocks"],
      "method": "Сопоставить ежедневные продажи и остатки"
    },
    {
      "id": "H2",
      "title": "Изменение цены",
      "datasets": ["sales"],
      "method": "Сравнить среднюю цену двух периодов"
    },
    {
      "id": "H3",
      "title": "Рост негативных отзывов",
      "datasets": ["reviews"],
      "method": "Сравнить рейтинг и долю негативных отзывов"
    }
  ],
  "limitations": [
    "Нет данных о рекламе",
    "Нет поисковых позиций"
  ]
}
```

## 4. Human-in-the-Loop

Менеджер получает экран:

```text
Период: последние 14 дней против предыдущих 14 дней

☑ Проверить остатки
☑ Проверить цену
☑ Проверить отзывы
☑ Сравнить с категорией
☐ Проверить возвраты

Комментарий:
[Сравни отдельно WB и Ozon]

[Утвердить и запустить]
[Пересобрать план]
[Отменить]
```

В MVP достаточно трёх действий:

```text
approve
revise
reject
```

Не делаем сложный редактор графа или ручное изменение каждой технической операции.

## 5. Execution Agent

После подтверждения агент получает:

* утверждённый план;
* подготовленные датасеты;
* бизнес-правила;
* нужный skill;
* примеры Python-кода.

Он пишет только glue-код анализа:

```python
from helpers.sales import compare_periods
from helpers.stocks import calculate_stockout_days
from helpers.growth import compare_with_category
```

То есть модель не изобретает все формулы заново.

## 6. Четыре skills

Skills оформляем локальными директориями с `SKILL.md`, примерами и проверенными helper-функциями. Официальная концепция Agent Skills также предполагает пакет файлов с обязательным `SKILL.md`, инструкциями и дополнительными скриптами. ([OpenAI Developers][3])

```text
skills/
├── sales-decline-analysis/
├── inventory-planning/
├── portfolio-growth/
└── reviews-and-pricing/
```

### `sales-decline-analysis`

Проверяет:

* продажи текущего и прошлого периода;
* выручку;
* среднюю цену;
* остатки;
* дни отсутствия товара;
* возвраты;
* отзывы;
* динамику категории;
* отдельно WB и Ozon.

### `inventory-planning`

Считает:

* средние продажи в день;
* количество дней запаса;
* предполагаемую дату окончания;
* рекомендуемый объём производства.

Формула MVP:

```text
Рекомендуемое производство =
спрос на период производства
+ страховой запас
− текущий остаток
− поставки в пути
```

Если поставок в пути нет в данных, считаем их равными нулю и явно показываем допущение.

### `portfolio-growth`

Формирует:

* топ-10 растущих;
* топ-10 падающих;
* рост относительно категории;
* абсолютный вклад в изменение продаж;
* фильтр слишком маленькой базы.

### `reviews-and-pricing`

Определяет:

* негативные отзывы;
* потенциально опасные жалобы;
* повторяющиеся проблемы;
* товары, требующие проверки цены.

# Покрытие вопросов из ТЗ

| Вопрос                               | Что делает MVP                                                                  |
| ------------------------------------ | ------------------------------------------------------------------------------- |
| Почему снизились продажи?            | Агент формирует гипотезы и проверяет продажи, остатки, цены, отзывы и категорию |
| Какие товары заканчиваются?          | Считает дни запаса                                                              |
| Что заказать в производство?         | Рассчитывает рекомендуемое количество по скорости продаж                        |
| Какие товары растут быстрее рынка?   | Сравнивает товар с его категорией или портфелем Mirrolla                        |
| Какие отзывы требуют реакции?        | Ранжирует отзывы по рейтингу, теме и повторяемости                              |
| Какие товары требуют изменения цены? | Выдаёт кандидатов на ценовой эксперимент                                        |

## Важные ограничения

### «Рынок»

В данных нет полной статистики рынка WB или Ozon.

В MVP фиксируем:

```text
Рынок = категория товаров внутри предоставленных данных Mirrolla
```

В интерфейсе и README это указывается явно.

### Цены конкурентов

В исходных данных, перечисленных в ТЗ, **нет источника цен конкурентов**.

Поэтому мы не можем честно определить новую оптимальную цену. MVP сможет только вернуть:

```text
рассмотреть снижение цены;
рассмотреть повышение;
сохранить цену;
недостаточно данных.
```

Для полноценной рекомендации понадобятся:

* цены конкурентов;
* себестоимость;
* комиссии;
* рекламные расходы;
* минимальная маржинальность.

### SEO карточек

В API 1С есть свойства продукта, но нет:

* поисковых позиций;
* показов;
* CTR;
* поисковых запросов;
* фактических заголовков карточек WB/Ozon;
* данных конкурентов.

Поэтому полноценный SEO-анализ в основной MVP не включаем. При наличии карточек можно сделать только аудит заполненности:

```text
название;
описание;
состав;
характеристики;
объём;
меры предосторожности;
противопоказания.
```

# Автоматический аналитический отчёт

Отчёт — это фиксированный workflow, а не полностью свободная работа агента.

```text
1. Топ-10 растущих товаров
2. Топ-10 падающих товаров
3. Товары с критическими остатками
4. Негативные отзывы
5. Кандидаты на изменение цены
6. Приоритетные рекомендации
```

Пример рекомендации:

```json
{
  "priority": "high",
  "product_code": "00-000123",
  "action": "Запустить производство",
  "reason": "Остатка хватит на 5 дней, расчётный цикл производства — 14 дней",
  "confidence": "high",
  "limitations": [
    "Не учтены поставки в пути"
  ]
}
```

# Архитектура MVP

```text
                        Streamlit UI
                             │
                             ▼
                         FastAPI
                             │
                 ┌───────────┴───────────┐
                 │                       │
          LangGraph Workflow        1C Connector
                 │                       │
          ┌──────┴──────┐                │
          │             │                │
   Planning Agent   Human Review          │
          │             │                │
          └──────┬──────┘                │
                 ▼                       │
        Approved Analysis Plan           │
                 │                       │
                 ▼                       │
       OpenAI Code Interpreter           │
                 │                       │
       Skills + Parquet datasets         │
                 │                       │
                 └──────────┬────────────┘
                            ▼
                       Result / Report
```

Docker Compose будет управлять сервисами приложения из одного YAML-файла и позволит запускать стек одной командой. ([Docker Documentation][4])

```text
docker compose up --build
```

Сервисы:

```yaml
services:
  api:
  ui:
```

Для MVP отдельный PostgreSQL можно не добавлять. Состояние HITL хранить в SQLite volume, а аналитические данные — в Parquet. Это снижает объём инфраструктурной работы.

# План на три дня

## День 1 — доступы, данные и расчёты

### Утро

1. Подключить OpenVPN.
2. Проверить доступность тестового сервера.
3. Исследовать способы вызова трёх функций 1С.
4. Зафиксировать реальные request/response.
5. Создать `OneCClient`.

### Далее

1. Изучить WB/Ozon выгрузки.
2. Зафиксировать соответствие колонок.
3. Сопоставить товары через `articleWb`, `articleOzon`, `gtin`.
4. Нормализовать данные.
5. Создать Parquet-файлы.
6. Написать helper-функции:

   * сравнение периодов;
   * дни запаса;
   * производственный заказ;
   * топ роста и падения;
   * негативные отзывы.

### Критерий готовности дня

Без LLM обычный Python-скрипт должен формировать:

```text
топ роста;
топ падения;
критические остатки;
план производства;
негативные отзывы.
```

Если к концу первого дня это не работает, агентную часть откладываем и продолжаем исправлять данные.

## День 2 — агент, skills и HITL

1. Создать четыре `SKILL.md`.
2. Добавить примеры расчётов.
3. Реализовать `AnalysisPlan`.
4. Собрать LangGraph:

   * inspect data;
   * select skill;
   * create plan;
   * interrupt;
   * execute;
   * finalize.
5. Подключить Code Interpreter.
6. Сделать экран утверждения плана.
7. Реализовать один полный сценарий:

```text
Почему снизились продажи товара?
```

### Критерий готовности дня

Полностью проходит цепочка:

```text
вопрос
→ гипотезы
→ подтверждение
→ Python-анализ
→ ответ
```

## День 3 — покрытие ТЗ и упаковка

### Первая половина дня

1. Критические остатки.
2. Производственный план.
3. Растущие и падающие товары.
4. Отзывы.
5. Ценовые сигналы.
6. Автоматический отчёт.

### Вторая половина дня

1. Docker Compose.
2. `.env.example`.
3. README.
4. Архитектурный документ до пяти страниц.
5. Тестовые сценарии.
6. Запись демонстрации.
7. Финальная проверка запуска с чистого окружения.

После середины третьего дня новые функции не добавляем.

# Что нужно уточнить до начала разработки

В твоём более детальном описании особенно важны:

1. Форматы и реальные колонки каждой выгрузки.
2. Размер файлов и количество строк.
3. Пример request/response каждой функции 1С.
4. Есть ли даты продаж внутри WB/Ozon выгрузок.
5. Есть ли исторические остатки или только текущий остаток.
6. Есть ли фактическая цена продажи.
7. Как представлены возвраты.
8. Есть ли категория товара.
9. Есть ли себестоимость.
10. Есть ли сроки производства и минимальные партии.
11. Есть ли вообще данные цен конкурентов.
12. Какие поля содержат отзывы.
13. Должен ли результат быть только в UI или выгружаться в Excel/PDF.

И ещё: доступы и VPN-конфигурацию не коммитим в Git. Они должны храниться только локально и передаваться приложению через `.env`; после завершения пилота опубликованные тестовые учётные данные желательно сменить.
