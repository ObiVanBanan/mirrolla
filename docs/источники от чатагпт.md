Серёга, для нашей задачи не стоит изучать весь LangChain. Нужен узкий маршрут:

```text
LangGraph State/Nodes/Edges
→ Planning workflow
→ Persistence + interrupt
→ Human Review
→ Code Interpreter
→ Skills
→ Parquet/DuckDB
→ пример целого проекта
```

## 1. База LangGraph — изучить первой

### Официальный бесплатный курс LangChain Academy

**Foundation: Introduction to LangGraph — Python** — самый системный старт: State, Nodes, Edges, persistence и Human-in-the-Loop. В курсе 55 уроков примерно на 6 часов. Я бы прошёл хотя бы первые модули и блок HITL. ([LangChain Academy][1])

Более короткая версия — **LangGraph Essentials — Python**. Там на практическом workflow разбираются State, Nodes, Edges и Memory. ([LangChain Academy][2])

### Документация, которую положить в NotebookLM

1. **LangGraph overview** — объясняет роль LangGraph как orchestration runtime для stateful и долгоживущих агентов. ([Docs by LangChain][3])
2. **Thinking in LangGraph** — очень полезный материал о том, как сначала разложить процесс на шаги, определить State, а затем превратить шаги в nodes. ([Docs by LangChain][4])
3. **Graph API overview** — технически объясняет State, Nodes, Edges, conditional edges и компиляцию графа. ([Docs by LangChain][5])
4. **Workflows and agents** — показывает разницу между фиксированным workflow и динамическим агентом, а также основные паттерны: routing, parallelization, orchestrator-worker и evaluator-optimizer. ([Docs by LangChain][6])

Для нашего MVP особенно важен **Thinking in LangGraph**. После него станет понятно, что:

```text
create_plan
human_review
execute_analysis
build_report
```

— это обычные nodes, а не четыре отдельных «магических агента».

## 2. Human-in-the-Loop: главная тема проекта

### Официальная документация LangGraph Interrupts

Это основной источник. Разбирает:

* `interrupt()`;
* приостановку графа;
* JSON-данные для UI;
* продолжение через `Command(resume=...)`;
* сохранение состояния;
* использование одного `thread_id`. ([Docs by LangChain][7])

### Persistence

Без checkpointer HITL нормально не работает. Этот раздел объясняет checkpoints, threads, восстановление состояния и продолжение workflow после паузы. ([Docs by LangChain][8])

### HITL middleware

Здесь хорошо показаны четыре варианта решения человека:

```text
approve
edit
reject
respond
```

Для нашего проекта понадобятся первые три. ([Docs by LangChain][9])

### Видео

**Human-in-the-Loop AI Agents in LangGraph — 2026 Walkthrough** — близко к нашему сценарию: node, сохранение контекста, approval/rejection loop. ([YouTube][10])

**LangGraph Agents for Beginners: Human in the Loop** — показывает HITL и для готового ReAct-агента, и для кастомного графа. ([YouTube][11])

**LangGraph: Persistence & Human-in-the-Loop Workflow** — отдельно разбирает checkpointers, threads, вмешательство человека и продолжение исполнения. ([YouTube][12])

**Fullstack LangGraph HITL с FastAPI и React** — полезно именно с точки зрения нашего API и UI: backend останавливает workflow, frontend получает pending action и возвращает решение. ([YouTube][13])

Начать я бы советовал с документации Interrupts, затем посмотреть одно видео и сразу сделать маленький тестовый граф:

```text
generate_plan → interrupt → approve → execute
```

## 3. Planning Agent и Approved Analysis Plan

### Workflows and Agents

В официальном гайде есть паттерны orchestrator-worker и evaluator-optimizer. Для нас важна сама идея: LLM формирует структурированный план, а граф исполняет его по контролируемым переходам. ([Docs by LangChain][6])

### Plan-and-Execute видео

**Build a Plan and Execute AI Agent Workflow with LangGraph** — демонстрирует отдельные стадии планирования и выполнения. Модель сначала строит план, затем executor проходит по шагам. ([YouTube][14])

**Building Effective Agents with LangGraph** — хорошее видео о различии workflow и agents и реализации основных агентных паттернов с нуля. ([YouTube][15])

### Лучший реальный пример под нашу архитектуру

Репозиторий **LangChain Open Deep Research**. В нём есть structured workflow с Human-in-the-Loop planning: сначала строится план отчёта, пользователь его проверяет и корректирует, после чего система выполняет исследование. По смыслу это почти наш сценарий:

```text
план отчёта
→ human approval
→ выполнение
→ итоговый документ
```

Только у нас вместо web research будет анализ Parquet-датасетов. ([GitHub][16])

Этот репозиторий я бы обязательно загрузил в NotebookLM или хотя бы отдельно изучил:

* схему State;
* узел создания плана;
* human feedback;
* переход после approval;
* обработку revisions;
* структуру итогового результата.

## 4. OpenAI Code Interpreter

### Основная официальная документация

**Code Interpreter Guide** — показывает, как дать модели Python sandbox, передать файлы, запускать код и получать созданные графики и файлы. ([OpenAI Developers][17])

Для нашего MVP это главный источник по исполнителю:

```text
approved_plan.json
+ sales.parquet
+ stocks.parquet
+ SKILL.md
→ Python sandbox
→ result.json + charts
```

### Responses API

Официальный пример Responses API полезен, чтобы понять:

* создание response;
* состояние между вызовами;
* подключение hosted tools;
* передачу результатов инструментов. ([OpenAI Developers][18])

### Практический пример анализа данных

В OpenAI Cookbook есть пример, где агент получает данные, генерирует Python и анализирует их через безопасный code interpreter. Это полезно для понимания самого цикла «модель написала код → получила ошибку → исправила → получила результат». ([OpenAI Developers][19])

Ещё один подходящий Cookbook-пример объединяет получение внешних цен и анализ CSV через Code Interpreter. Это близко к будущему сценарию Mirrolla с ценами конкурентов. ([OpenAI Developers][20])

### Видео

**Responses API Beginner Tutorial** — короткий обзор Responses API и подключения Code Interpreter. Используй как визуальное дополнение, но код сверяй с текущей официальной документацией. ([YouTube][21])

**Responses API: Advanced File Analysis** — пример анализа табличного файла через Responses API. ([YouTube][22])

Старые видео про Assistants API лучше смотреть только для понимания идеи. Для новой реализации ориентируйся на **Responses API**, а не строй MVP вокруг старого Assistants API.

## 5. Skills и `SKILL.md`

### Официальное руководство OpenAI

**Skills Guide** объясняет основной формат:

```text
skill-name/
├── SKILL.md
├── scripts/
├── references/
└── assets/
```

Skill является версионируемым набором файлов, а `SKILL.md` содержит метаданные и инструкции. ([OpenAI Developers][23])

### Практический Cookbook

**Skills in OpenAI API** показывает загрузку, версионирование и подключение skills к окружению. ([OpenAI Developers][24])

### Как проектировать хорошие skills

Статья OpenAI **Testing Agent Skills Systematically with Evals** особенно полезна. Там объясняется:

* сначала определить критерии успеха;
* сделать короткий `SKILL.md`;
* проверить, когда skill должен и не должен срабатывать;
* собрать небольшой набор тестовых prompts;
* проверять outcome, process и efficiency. ([OpenAI Developers][25])

Ещё одна полезная статья объясняет progressive disclosure: сначала агент видит только `name` и `description`, а полный `SKILL.md`, scripts и references загружаются после выбора skill. ([OpenAI Developers][26])

### Видео

**What Are Skills? Build Your First AI Agent Skill** — простой визуальный разбор `SKILL.md`, scripts и references. ([YouTube][27])

**Skills.md from Scratch: Skill-Driven Coding Agent** — полезен для понимания metadata-first подхода и загрузки инструкций по необходимости. ([YouTube][28])

Для нашего проекта первый skill должен быть только один:

```text
sales-decline-analysis/
├── SKILL.md
├── scripts/
│   └── helpers.py
├── examples/
│   └── analysis_example.py
└── references/
    └── data_dictionary.md
```

Когда полный цикл заработает, скопируем паттерн для остатков и отзывов.

## 6. Parquet, PyArrow и DuckDB

### Официальная документация Apache Arrow

**Reading and Writing Parquet** — базовое руководство по чтению и записи Parquet через PyArrow и pandas. ([Apache Arrow][29])

**PyArrow Datasets** — показывает работу с несколькими файлами, партициями, выбором колонок и фильтрацией больших наборов данных. ([Apache Arrow][30])

Для MVP достаточно знать:

```python
df.to_parquet("sales.parquet", index=False)
df = pd.read_parquet("sales.parquet")
```

и уметь посмотреть schema.

### Хабр про Parquet

**Гайд: как работать с форматом Parquet** — свежий русскоязычный обзор формата и работы с ним через Python. ([Habr][31])

### DuckDB

**Работа с данными в DuckDB, или не pandas’ом единым** — практическая статья о чтении CSV/Parquet, объединении файлов и аналитике SQL-запросами. ([Habr][32])

**DuckDB: колоночная OLAP-СУБД в кармане** — хороший обзор возможностей DuckDB, оконных функций, SQL-аналитики и интеграции с Python. ([Habr][33])

Для нашего MVP DuckDB может оказаться удобнее чистого pandas:

```python
import duckdb

result = duckdb.sql("""
    SELECT
        product_code,
        SUM(quantity) AS sales
    FROM read_parquet('/workspace/data/sales.parquet')
    GROUP BY product_code
""").df()
```

Агенту проще генерировать прозрачные SQL-запросы, чем длинные цепочки преобразований pandas.

## 7. Самая релевантная статья на Хабре для нашего проекта

**Как мы отучали LLM выдумывать цифры в данных**.

Авторы пришли примерно к тем же решениям, которые обсуждаем мы:

* числа должен считать аналитический движок;
* SQL использовать там, где задача выражается через SQL;
* сложную аналитику выполнять через Python sandbox;
* давать модели чёткое описание схемы данных;
* не заставлять LLM угадывать содержимое таблиц. ([Habr][34])

Её стоит изучить одной из первых, потому что это практически описание основных рисков Mirrolla AI Data Analyst.

## 8. Полезные статьи с Хабра по архитектуре агентов

### «От LangChain к LangGraph»

Подробно объясняет переход от линейных цепочек к графам с состоянием и сложными переходами. ([Habr][35])

### «Создание умных AI-агентов: полный курс по LangGraph»

Русскоязычная серия о моделях, инструментах, доступе к файлам и построении агентов с практическими примерами. ([Habr][36])

### «Агентные системы для продакшена»

Полезна не для первого прототипа, а для понимания инфраструктуры: HITL, checkpointer, gateway, наблюдаемость и эксплуатация. ([Habr][37])

### «Pipeline Triad Pattern»

Интересный материал о сочетании Human-in-the-Loop и Human-on-the-Loop: человек утверждает стратегию и контрольные точки, а агент автономно выполняет работу между ними. Это почти точное описание нашей концепции. ([Habr][38])

### «Создание эффективных агентов»

Русский перевод известного материала о разнице между workflows и agents. Хорошо помогает не превратить проект в бесконтрольного автономного агента. ([Habr][39])

### «Мультиагентный хаос»

Полезный критический материал о том, почему явный контроллер состояния часто надёжнее свободного общения нескольких агентов. Для нас это аргумент в пользу одного LangGraph workflow, а не multi-agent системы. ([Habr][40])

   create_plan → human_review → execute → finalize.

3. Покажи минимальный пример interrupt() и Command(resume=...).

4. Как сохранять граф между HTTP-запросами FastAPI?

5. Как пользователь может отредактировать план перед продолжением?

7. Как оформить sales-decline-analysis как SKILL.md?

8. Какие части анализа должны быть LLM-driven,
