Серёга, честно:

## Полную задуманную систему за 3 дня мы не сделаем

Под полной системой я понимаю:

* универсальный агент над любыми датасетами;
* автоматическое исследование схем;
* динамический выбор skills;
* полноценный Human-in-the-Loop с сохранением и восстановлением состояния;
* собственный безопасный sandbox;
* проверку всех рассчитанных метрик;
* интеграцию с 1С;
* отчёты;
* UI;
* Docker;
* тесты;
* архитектурный документ.

Это примерно **1,5–3 недели работы**, даже при активном использовании AI. Главный риск — не LLM, а данные: несовпадающие SKU, странные форматы дат, возвраты, пропуски, разные структуры WB и Ozon.

Но **демонстрационный MVP этой концепции за 3 плотных дня сделать можно**. Вероятность успеть я бы оценил примерно в **65–75%**, если выгрузки и описание тестового API будут доступны в первый день.

# Что войдёт в MVP

## 1. Один универсальный Data Analysis Agent

Он будет:

1. получать вопрос;
2. изучать краткое описание доступных файлов;
3. выбирать подходящий skill;
4. формировать гипотезы и план;
5. ждать решения человека;
6. выполнять анализ в Python sandbox;
7. возвращать вывод, таблицу и график.

```text
Вопрос
  ↓
Planning Agent
  ↓
План и гипотезы
  ↓
Approve / Edit
  ↓
Execution Agent
  ↓
Code Interpreter
  ↓
Результат
```

Для sandbox не будем писать собственный Docker runner. Используем OpenAI Code Interpreter: это уже изолированная среда, где модель может запускать Python и работать с загруженными файлами. ([OpenAI Developers][1])

## 2. Один Human-in-the-Loop checkpoint

Только одна точка подтверждения:

```text
Агент сформировал план
        ↓
Менеджер:
[Запустить]
[Изменить]
[Отменить]
```

Не будем делать подтверждение каждого tool call или каждой строки кода.

LangGraph позволяет остановить выполнение через `interrupt()`, сохранить состояние и продолжить после ответа человека. Для этого нужен checkpointer и стабильный `thread_id`. ([Docs by LangChain][2])

## 3. Четыре простых skills

Не полноценная динамическая skill-платформа. Просто четыре директории с `SKILL.md`, примерами и вспомогательными функциями:

```text
skills/
├── sales-analysis/
│   ├── SKILL.md
│   └── helpers.py
├── inventory-planning/
│   ├── SKILL.md
│   └── helpers.py
├── growth-analysis/
│   ├── SKILL.md
│   └── helpers.py
└── review-price-analysis/
    ├── SKILL.md
    └── helpers.py
```

Skills официально представляют собой набор инструкций, ресурсов и необязательных скриптов. Но в MVP мы не будем строить отдельный загрузчик и систему версий — просто положим их в репозиторий и будем передавать нужный skill агенту. ([OpenAI Developers][3])

### `sales-analysis`

Закрывает:

* почему снизились продажи;
* сравнение периодов;
* влияние наличия;
* изменение цены;
* возвраты;
* сравнение с категорией.

### `inventory-planning`

Закрывает:

* какие товары заканчиваются;
* на сколько дней хватит остатка;
* что заказать в производство;
* рекомендуемый объём заказа.

### `growth-analysis`

Закрывает:

* топ растущих;
* топ падающих;
* рост относительно категории;
* защита от эффекта маленькой базы.

### `review-price-analysis`

Закрывает:

* негативные отзывы;
* приоритет реакции;
* повторяющиеся жалобы;
* сигналы для изменения цены.

## 4. Файлы загружаются заранее

В MVP агент не будет каждый раз вызывать сложные tools экспорта.

При запуске анализа в контейнер передаём подготовленный пакет:

```text
/workspace/data/
├── sales_wb.parquet
├── sales_ozon.parquet
├── stocks.parquet
├── products.parquet
├── reviews.parquet
├── business_rules.json
└── data_dictionary.md
```

Это сильно сокращает разработку.

В production можно добавить:

```text
list_datasets
get_dataset_schema
export_dataset
```

Но сейчас это лишний слой.

## 5. Простая интеграция с тестовой 1С

Не делаем полноценную синхронизационную платформу.

Будет один endpoint:

```http
POST /api/sync/1c
```

Он:

1. получает товары;
2. получает продажи;
3. получает остатки;
4. сохраняет нормализованные данные;
5. формирует Parquet-файлы.

Без:

* расписания;
* фоновых задач;
* retry queue;
* инкрементальной синхронизации;
* сложного журналирования;
* отправки данных обратно в 1С.

## 6. Автоматический отчёт

Отдельная кнопка:

```text
[Сформировать отчёт менеджера]
```

Для неё используется заранее подготовленный запрос:

```text
Сформируй отчёт за последние 14 дней:

1. Топ-10 растущих товаров.
2. Топ-10 падающих товаров.
3. Критические остатки.
4. Негативные отзывы.
5. Рекомендации менеджеру.
```

Агент составляет план, но для демонстрации этот план можно автоматически считать утверждённым либо показать тот же экран подтверждения.

# Как будет выглядеть пользовательский сценарий

## Шаг 1. Менеджер задаёт вопрос

```text
Почему снизились продажи шампуня с кератином?
```

## Шаг 2. Агент формирует план

```text
Товар:
Шампунь с кератином 400 мл

Период:
Последние 14 дней против предыдущих 14 дней

Гипотезы:

☑ H1. Товар отсутствовал на складе.
☑ H2. Изменилась средняя цена.
☑ H3. Выросло количество негативных отзывов.
☑ H4. Снизился спрос во всей категории.
☑ H5. Выросла доля возвратов.

Не могут быть проверены:

— изменение рекламы: данные отсутствуют;
— позиции в поиске: данные отсутствуют.
```

Менеджер может написать:

```text
Убери проверку возвратов.
Сравни отдельно WB и Ozon.
Возьми период 30 дней.
```

## Шаг 3. Агент выполняет Python-код

Он получает:

* утверждённый план;
* релевантный `SKILL.md`;
* примеры;
* датасеты;
* бизнес-правила.

Агент пишет glue-код, но формулы берёт из готовых helper-функций:

```python
from skills.sales_analysis.helpers import (
    compare_equal_periods,
    calculate_stockout_days,
    calculate_return_rate,
    compare_with_category,
)
```

## Шаг 4. Возвращает результат

```text
Продажи снизились на 24,3%.

Подтверждённые сигналы:

1. Товар отсутствовал на складе 4 дня из 14.
2. Продажи на WB снизились на 31%, на Ozon — на 8%.
3. Средняя цена на WB выросла на 7,2%.
4. Категория снизилась только на 3,1%.

Не подтверждено:

— общий спад категории;
— значительный рост возвратов.

Вероятная причина:
дефицит товара на WB в сочетании с повышением цены.

Рекомендации:

1. Восстановить запас на WB.
2. Не проводить новое повышение цены.
3. Повторить анализ через 7 дней после пополнения.

Ограничения:
нет данных о рекламе, показах и конверсии.
```

Плюс график продаж, цены и остатков.

# Что точно вырезаем

## Не будет собственного sandbox

Это отдельная инфраструктурная задача:

* защита хоста;
* ограничение сети;
* CPU/RAM limits;
* timeout;
* уничтожение контейнеров;
* передача файлов;
* сбор артефактов.

Используем готовый Code Interpreter.

## Не будет настоящей универсальности

Агент сможет работать с предоставленными Mirrolla-датасетами, но не с любым произвольным CSV.

Мы заранее подготовим:

```text
data_dictionary.md
business_rules.json
нормализованные названия колонок
сопоставление SKU
```

## Не будет полноценного валидатора

Не будем повторно пересчитывать каждую цифру отдельным сервисом.

Вместо этого:

* проверенные helper-функции;
* JSON-схема результата;
* sanity checks;
* обязательное отображение периода;
* обязательное отображение ограничений.

Например:

```python
assert current_period_days == previous_period_days
assert current_sales >= 0
assert stock_days >= 0
assert -100 <= sales_change_percent
```

## Не будет настоящего прогнозирования спроса

Только прозрачная формула:

```text
средние продажи за 7/28 дней
× горизонт планирования
+ страховой запас
− текущий остаток
```

Без Prophet, XGBoost, LSTM и сложного ML.

## Не будет автоматической установки цены

Только рекомендации:

```text
рассмотреть снижение;
сохранить цену;
рассмотреть тестовое повышение;
данных недостаточно.
```

## Не будет production-ready состояния

Один пользователь, одна демонстрационная среда, ограниченное количество одновременных запусков.

# Минимальный стек

```text
Streamlit
FastAPI
LangGraph

Pandas / Parquet

```

## День 1 — данные и аналитические helpers

Главная цель: все расчёты должны работать без агента.

Сделать:

* изучение файлов;
* нормализацию колонок;
* сопоставление SKU;
* перевод в Parquet;
* клиент тестовой 1С;
* четыре набора helper-функций;

Критерий готовности:

```text
Обычный Python-скрипт уже формирует

```

Если день 1 уйдёт только на борьбу с данными, функционал придётся сокращать.

Сделать:

* один рабочий skill сначала;

Критерий готовности:

```text
Вопрос о падении продаж проходит полный цикл:
вопрос → план → approve → Python → ответ.
```

Сделать:

Если начинаем не успевать, режем в таком порядке:

### Сначала убираем

1. редактирование отдельных гипотез через сложную форму;
2. сохранение истории всех запусков;
3. графики для каждого ответа;
4. SEO-анализ;
5. полноценные рекомендации по цене.

### Оставляем обязательно

1. анализ падения продаж;
2. критические остатки;
3. производственный план;
4. негативные отзывы;
5. автоматический отчёт;

8. Docker Compose и README.

# Моя итоговая оценка

**Полную платформу — нет, не успеем.**

**Демо-MVP с одним агентом, одной точкой HITL, четырьмя простыми skills и hosted sandbox — успеть можно**, но только при жёсткой дисциплине:

* сначала расчёты;
* потом агент;
* потом UI;
* никакой самописной инфраструктуры;
* никакого сложного ML;
* демонстрация на заранее проверенных вопросах.

Самый опасный сценарий — потратить первые два дня на красивую агентную архитектуру, а на третий обнаружить, что WB и Ozon невозможно нормально связать по товарам. Поэтому первый рабочий результат должен быть не чат, а **Python-отчёт по реальным выгрузкам**. Затем мы оборачиваем его в агентный workflow.
