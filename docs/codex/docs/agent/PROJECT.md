# Проект и продуктовая модель

## Пользователь

Основной пользователь — менеджер маркетплейсов. Он понимает бизнес-контекст, но часто не умеет заранее сформулировать:

- точную метрику;
- корректные периоды сравнения;
- уровень агрегации;
- набор проверяемых гипотез;
- ограничения доступных выгрузок.

Система не должна требовать от менеджера знания pandas, SQL или внутренней схемы файлов.

Менеджер также не должен вручную копировать выгрузки в серверную папку. Он загружает файлы через frontend, видит их статус и явно выбирает, какие версии использовать в конкретном анализе.

## Проблема

Менеджер регулярно анализирует продажи, остатки, отзывы, динамику спроса и производственные потребности. Данные приходят из разных систем и могут менять физическую структуру. Статичный набор отчётов не покрывает все вопросы, а свободный LLM-анализ без ограничений ненадёжен.

## Ценность продукта

Mirrolla объединяет четыре свойства:

1. **Помощь в постановке задачи** — skill и Planner превращают неясный вопрос в понятный план.
2. **Гибкость** — модель пишет Python-код под фактические данные текущей загрузки.
3. **Контроль** — manifest и deterministic validators ограничивают допустимый результат.
4. **Объяснимость** — пользователь видит план, assumptions, limitations и итоговые findings.

## Текущие аналитические направления

- `sales-decline-analysis` — причины падения продаж.
- `inventory-planning` — критические остатки и объём производства.
- `portfolio-growth` — рост и падение товаров относительно внутренних категорий.
- `reviews-and-pricing` — отзывы, темы для реакции и качественные ценовые выводы при наличии данных.

Названия конкретных skills следует проверять по `agent/schemas.py` и `agent/skills/` перед изменением.

## Нормальный пользовательский сценарий

```text
Менеджер загружает Ozon XLSX и WB CSV через панель «Данные».
Система проверяет и профилирует файлы.
Менеджер выбирает готовые версии.

Менеджер: «Посмотри, почему плохо продаётся этот товар»

Система:
1. распознаёт товар и intent;
2. предлагает периоды и гипотезы;
3. показывает доступные и отсутствующие данные;
4. получает approve/revise/reject;
5. выполняет анализ;
6. возвращает выводы с цифрами и ограничениями.
```

Пользователю не нужно показывать Python-код до исполнения. Код сохраняется для воспроизводимости и технического аудита.

## Что проектом не является

- универсальный data science notebook без доменной методики;
- LLM, который получает Excel и делает что угодно;
- жёсткий набор CRUD-style analytics tools;
- RAG-система по табличным продажам;
- multi-agent система ради количества агентов;
- полноценный SaaS с multi-tenancy на текущем этапе.

## Истина и изменяемые факты

### Долгоживущая истина

- смысл метрик;
- правила сравнения периодов;
- минимальная статистическая значимость;
- правила priority;
- какие выводы нельзя делать без определённых данных;
- output contract и validation invariants.

### Изменяемые факты

- filenames;
- названия листов и колонок;
- количество строк;
- доступный диапазон дат;
- набор маркетплейсов;
- наличие цен, истории остатков или заказов WB;
- внутренние URL и credentials.

Долгоживущая истина живёт в skill/validator. Изменяемые факты выводятся из dataset registry, profile и runtime configuration.

## Принцип владения данными

Uploaded raw file является immutable DatasetVersion. Пользователь может загрузить новую version, но старый analysis продолжает ссылаться на прежний checksum. Filename является отображаемой metadata и никогда не заменяет version identity.
